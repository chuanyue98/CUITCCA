# GraphRAG 调研评估：为什么校园助手用 Agent 多跳，而不是图索引

> 调研日期：2026-08　适用版本：v0.3+（自动路由 + Agent 多跳已上线）
> 本文是面试常问的"你们为什么不用 GraphRAG？"的完整论证稿——先讲清楚 GraphRAG
> 解决什么问题、在什么数据上有效，再对照本项目的实际数据说明为什么校园场景
> 选择"Agent 多跳"而不是图索引，最后给出什么条件下应该转向/叠加 GraphRAG。

---

## 1. 结论先行

**在 campus-corpus 这种"政策/流程/规章"型语料上，Agent 多跳检索（本项目现状）
比 GraphRAG 更划算：成本低一个量级，收益没有可测的差异，且每一条检索质量
改进都有 golden 评测数据支撑。** 如果未来语料变成"实体关系密集"（科研团队
合作网络、课程先修关系、组织沿革），再评估引入 GraphRAG——那是它的主场，
两者不矛盾，可以叠加。

一句话版（面试可以直接说）：

> GraphRAG 的收益来自"全局性问题"——需要聚合跨文档的实体关系才能回答的
> 问题。校园助手的真实问题分布里这类问题占比极低（语料 76 题 golden 集里
> 只有 2 题属于"跨文档聚合"类，且都能靠单次检索 + 置信度路由解决），而
> GraphRAG 的构建成本（每文档 LLM 实体抽取 + 社区检测 + 摘要）是固定开销，
> 与问题分布无关。用 Agent 多跳把"多跳"做成**按需触发**，成本随问题分布
> 自适应，这才是校园 FAQ 场景的最优解。

---

## 2. GraphRAG 是什么，它解决了什么

Microsoft GraphRAG（2024.07 论文）的核心机制：

1. **索引阶段**：对每个文档用 LLM 抽取实体（人名、机构、事件…）与关系，构建
   知识图谱；对图谱做社区检测（leiden），为每个社区生成层级化摘要。
2. **查询阶段**：
   - **全局搜索**（global search）：把社区摘要汇总成 map-reduce 式的多轮 LLM
     调用，回答"这个语料里有哪些……"这类需要看全貌的问题。
   - **局部搜索**（local search）：先从图谱里定位与问题相关的实体，沿边扩展
     一跳/两跳邻居，把邻居的原文文本喂给 LLM 生成。

它真正改变的是**"跨文档聚合"这一类问题**的答案质量：普通 RAG 每次只看到
top-k 个孤立片段，图索引能让模型看到"哪些实体之间有关联"，从而回答"A 和 B
有什么关系""哪些部门都涉及这个事项"这类问题。

RAGFlow 等平台对 GraphRAG 的落地大体就是这个机制（实体抽取模型 + 图存储 +
社区摘要），只是把 Microsoft 的实现工程化、可视化。

## 3. 本项目现状：Agent 多跳是怎么工作的

对照一下本项目已有的"多跳"能力（`backend/app/agents/` + `handlers/auto_router.py`）：

- **FunctionAgent**：模型自己决定调哪个工具、调几次。工具集包括
  `search_knowledge_base`（混合检索）、`list_knowledge_bases`（先看目录）、
  `get_document_chunks_by_source`（按来源取原文）。第一跳检索置信度不够时，
  模型可以换一个角度/换一份语料再查。
- **自动路由**：先按 standard 路径检索一次，**重排后的 top1 分数**
  （cross-encoder，实测覆盖问题 0.73~0.99、未覆盖问题 0.01~0.50，区分度极好）
  低于 `AUTO_ROUTE_SCORE_THRESHOLD`（0.6）才升级到 Agent。也就是说"多跳"是
  **按需触发的**——绝大多数问题单跳就够，多跳的延迟/token 成本只在少数问题
  上发生。
- **数据支撑**：76 题 golden 集检索 hit_rate 97.37% / MRR 0.858，其中
  `multi_hop` 档 10 题 hit_rate 100%——"需要多跳"的问题子集本来就是语料里
  占比最小的部分，而且现有链路已经覆盖得很好。

关键对照：**GraphRAG 的构建成本在索引阶段就全额支付（与查询分布无关）；
Agent 多跳的成本在查询阶段按需支付（与问题分布自适应）。** 这是两种架构的
根本差异，也是本文论证的核心。

## 4. 校园语料特征分析：为什么图谱收益低

`data/corpus`（静态语料 + Web 连接器采集）的真实构成：

| 内容类型 | 典型例子 | 答案形态 |
|---|---|---|
| 流程/办事指南 | 休学复学流程、转专业流程、证件补办 | **单一流程文档**内的步骤序列 |
| 规章制度 | 借阅规则、公寓管理、奖学金标准 | 单份规章内的条款 |
| 事实速查 | 图书馆开馆时间、校车时刻、联系方式 | 单条事实，通常就在 1 份文档里 |
| 表格数据 | 校车时刻表、历任领导、收费标准 | 表格被感知切块后整体可检索 |

三条直接结论：

1. **实体稀疏**：校园政策文本不是"人物关系网"。实体以"部门 + 事项 + 条件"
   为主，一个问题的答案几乎总是落在 1~2 份文档里，不需要沿图谱边跨文档聚合。
   GraphRAG 最值钱的"社区摘要"在实体稀疏的语料上几乎抽不出有意义的社区。
2. **问题形态是"怎么办/多少钱/什么条件"**：这些是局部事实查询（local），
   不是"有哪些/有什么关系"的全局查询（global）。全局查询在校园场景里的自然
   例子极少——"学校对困难学生的帮扶政策整体情况"这类问题，76 题 golden 集
   里都不存在。
3. **多跳的真实形态是"换个角度查"**：校园问题所谓的"多跳"，更多是"第一跳
   措辞不对没召回，换个说法/换份语料再查"（Agent 工具已覆盖），而不是"沿着
   实体关系链推导"。后者才需要图。

## 5. 成本收益量化对照

以下数字基于本项目真实配置（bge-m3 本地嵌入、gpt 级别 OpenAI 兼容 LLM、
campus-corpus 语料规模约数百篇文档）：

| 维度 | GraphRAG（若引入） | Agent 多跳（现状） |
|---|---|---|
| 索引构建成本 | **每篇文档一次 LLM 实体抽取**（约 1~3k token/篇）+ 社区检测 + 摘要（社区数 × 摘要 token）——数百篇语料 = 数十万 token 的一次性固定开销 | 零（摄取链路只有本地嵌入，无 LLM） |
| 语料更新成本 | 实体/关系失效，需要**重跑受影响子图的抽取与摘要**，增量维护复杂 | 增量摄取管道已支持（UPSERTS 去重 + 内容 hash），新增文档零额外图谱开销 |
| 查询成本 | 全局搜索：多轮 map-reduce（数十次 LLM 调用）；局部搜索：图谱遍历 + 原文喂入 | 单跳 1 次 LLM；多跳按需（自动路由只把低置信度问题升级） |
| 查询延迟 | 全局秒级~分钟级；局部百毫秒级 + 图谱遍历 | 单跳与现有 QA 一致；多跳多一轮工具往返 |
| 可评测性 | 社区摘要质量难自动化评测；图谱构建误差会静默传播 | 76 题 golden 集 hit_rate/MRR 全链路可测，实测 97.37% / 0.858 |
| 失败模式 | 实体抽取错误 → 图里缺边/错边 → 查询静默漏召回 | 检索不到 → 置信度信号明确 → 路由升级/兜底文案显式降级 |

一个反直觉的点：**GraphRAG 的索引成本在"问题分布"之外全额支付**。如果 90%
的问题单跳就能答好，GraphRAG 为剩下 10% 可能受益的问题，付出了 100% 文档的
图谱构建成本；而 Agent 多跳只为那 10% 的问题付出额外成本。在"问题分布高度
倾斜于简单问题"的校园场景，这个差异是决定性的。

## 6. 什么情况下应该转向/叠加 GraphRAG

诚实地说，下面这些场景出现时，图索引会变成合理选择——校园助手未来如果往
这个方向扩展，路线是**叠加**而不是替换：

1. **语料实体关系变密集**：例如引入科研团队网络（师生-项目-成果-期刊）、
   课程知识图谱（先修关系、知识点的前置依赖）。此时"沿着关系链回答"成为
   真实高频需求，图谱的局部搜索才发挥价值。
2. **全局性问题成为产品主线**：如"学校资助体系全景""本科四年可以修哪些
   方向的课"这类需要聚合多份文档的问题。判据很简单：数一下线上查询里以
   "有哪些/整体情况/关系"开头的问题占比，超过 ~20% 就值得做。
3. **评测能证明收益**：在 golden 集上把"+GraphRAG 局部搜索"作为一条检索
   路径与现有混合检索 A/B——如果 hit_rate/MRR 没有显著提升，就说明语料里
   还没有图能发挥的空间。这是本项目一贯的选型纪律（混合检索、rerank、
   查询改写都是这么验证的）。

如果要做，建议的最小接入路径（不推翻现有架构）：

```
查询 -> 自动路由（现状） --全局类问题--> GraphRAG 局部搜索（新增一条检索路径）
                        --常规问题-----> 现有混合检索 + 重排（不动）
```

即把 GraphRAG 作为**自动路由的一条新分支**，而不是替代现有检索——和 Agent
的引入方式完全一致：新增端点/路径，用评测数据决定是否值得保留。

## 7. 面试问答速记

**Q：为什么不用 GraphRAG？**
A：GraphRAG 解决的是"跨文档实体聚合"类问题，成本在索引阶段全额支付。校园
语料实体稀疏、问题高度倾斜于单文档事实/流程查询，图索引的收益在 golden 集
上测不出来，成本却是固定的。我们用自动路由 + Agent 多跳把"多跳"做成按需
触发，76 题 golden 集 hit_rate 97.37% / MRR 0.858 都有数据支撑。

**Q：那你们的多跳和 GraphRAG 的多跳有什么区别？**
A：我们的"多跳"是检索层面按需再查（换措辞、换语料、按来源取原文），
GraphRAG 的"多跳"是沿着实体关系边推理。校园政策文本的"多跳"主要是前者；
后者在科研网络、课程先修这类关系密集语料上才有意义，那是明确的扩展路线。

**Q：如果你们引入 GraphRAG，怎么接入？**
A：作为自动路由的一条新分支——全局类问题走 GraphRAG 局部搜索，常规问题
保持现有混合检索。先做 A/B 评测，hit_rate/MRR 没有显著提升就不保留。我们
的选型纪律是数据说话（混合检索、rerank 都是这么验证的）。
